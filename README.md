# SLAE Solver

Веб-застосунок для розв'язання великих систем лінійних алгебраїчних рівнянь (СЛАР) методом Гаусса з балансуванням навантаження, чергою задач та оновленням прогресу в реальному часі.

> Навчальний проєкт. Нижче описані вимоги, архітектура та поточний стан реалізації.

## 1. Мета 

Користувач задає розмір матриці (генерується випадкова) або завантажує власну, система розв'язує СЛАР (до 5000×5000) і показує прогрес виконання.


## 2. Технології

- **Frontend:** React (Vite) + Tailwind CSS
- **Backend:** Python, FastAPI
- **База даних:** PostgreSQL, SQLAlchemy, Alembic (міграції)
- **Черга задач:** Celery + Redis
- **Балансувальник / reverse proxy:** Nginx
- **Контейнеризація:** Docker, Docker Compose (Docker SDK для автоскейлінгу)
- **Real-time:** WebSocket (FastAPI) + Redis Pub/Sub
- **Авторизація:** JWT (PyJWT), хешування паролів bcrypt
- **Шифрування трафіку:** HTTPS (TLS) на Nginx

## 3. Архітектура

```
Browser ──HTTPS──► Nginx ──► api1 ┐
                             api2 ┤──► PostgreSQL (користувачі, задачі)
                             apiN ┘        ▲
                               │ publish   │
                               ▼           │
                             Redis ◄───────┤
                       (Celery broker +    │
                        Pub/Sub прогрес)   │
                               │ consume   │
                               ▼           │
                         worker-1..M ──────┘
                               ▲
                       autoscaler (Docker SDK)
```



### Компоненти

- **Nginx** приймає весь трафік на одній адресі. Як reverse proxy передає запити на API-сервери, як балансувальник розподіляє їх алгоритмом `least_conn`. Завершує TLS: ззовні з'єднання шифроване (HTTPS), всередині Docker-мережі трафік між Nginx і API передається по HTTP. Також проксіює WebSocket (заголовки `Upgrade`/`Connection`) і пізніше роздаватиме фронтенд.
- **API-сервери (FastAPI, `api1`, `api2`)** обробляють авторизацію, валідацію, створення задач, історію та WebSocket. Вони не мають стану в пам'яті: токени перевіряються за підписом (однаковий `SECRET_KEY` на всіх серверах), прогрес іде через Redis. Тому запит може обробити будь-який сервер, а sticky sessions не потрібні.
- **PostgreSQL** зберігає користувачів і задачі (статус, розмір, прогрес, часові мітки, помилки).
- **Redis** виконуватиме дві ролі: брокер черги Celery і канал Pub/Sub для прогресу задач.
- **Celery-воркери** виконуватимуть розв'язання СЛАР методом Гаусса (NumPy), оновлюватимуть прогрес у БД та публікуватимуть його в Redis.
- **Autoscaler** (окремий сервіс, запланований) стежитиме за довжиною черги та через Docker SDK запускатиме або зупинятиме контейнери воркерів у межах ліміту.
- **migrate** одноразовий контейнер, що виконує `alembic upgrade head` перед стартом API. Таблиці створює саме він, щоб `api1` та `api2` не конфліктували при одночасному старті.

### Авторизація

1. `POST /auth/register`: пароль хешується bcrypt, користувач зберігається в таблиці `users`. Пароль у відкритому вигляді не зберігається.
2. `POST /auth/login`: пароль звіряється з хешем, видається JWT з id користувача та терміном дії.
3. Захищені запити передають токен у заголовку `Authorization: Bearer <token>`. Сервер перевіряє підпис і термін дії без звернення до бази за сесією.

### Життєвий цикл задачі (план)

1. Клієнт надсилає запит, Nginx передає його на один з API-серверів.
2. API перевіряє ліміти (розмір, кількість задач користувача) і за перевищення одразу повертає помилку.
3. API створює запис `Task` зі статусом `QUEUED` і ставить задачу в чергу Celery через Redis.
4. Вільний воркер бере задачу, ставить `RUNNING` і розв'язує систему, періодично оновлюючи прогрес.
5. Прогрес публікується в Redis-канал `task:{id}`, API через WebSocket пересилає його клієнту.
6. Завершення дає статус `DONE`, помилка або перевищення часу `FAILED`, скасування `CANCELLED`.

### Скасування, ліміти, черга (план)

- **Скасування:** API записує в Redis прапорець `cancel:{id}`, solver перевіряє його в циклі по рядках і завершується.
- **Ліміт часу:** `soft_time_limit` Celery.
- **Черга:** якщо всі воркери зайняті, задачі чекають у Redis. Оцінка очікування: `(задач у черзі / кількість воркерів) × середній час виконання`.

## 5. Запуск

Потрібні Docker, Docker Compose та `openssl`.

### Крок 1. Згенерувати самопідписаний сертифікат

Папка `nginx/certs/` не зберігається в git (там приватний ключ), тому її потрібно створити перед першим запуском:

```bash
mkdir -p nginx/certs
openssl req -x509 -nodes -newkey rsa:2048 -days 365 \
  -keyout nginx/certs/selfsigned.key \
  -out nginx/certs/selfsigned.crt \
  -subj "/CN=localhost" \
  -addext "subjectAltName=DNS:localhost,IP:127.0.0.1"
```

### Крок 2. Запустити

```bash
docker compose up --build -d
docker compose ps -a
```

Сервіс `migrate` має завершитися зі статусом `Exited (0)`, решта сервісів `Up`.

### Крок 3. Перевірити

Балансування (відповіді чергуються між `api1` та `api2`; `-k` потрібен через самопідписаний сертифікат):

```bash
for i in 1 2 3 4 5 6; do curl -sk https://localhost/api/whoami; echo; done
```

Swagger-документація API: `https://localhost/api/docs`. Браузер попередить про незахищене з'єднання, бо сертифікат самопідписаний; для навчального проєкту це очікувано.


### Змінні середовища

| Змінна | Призначення | Значення за замовчуванням |
|---|---|---|
| `DATABASE_URL` | Адреса PostgreSQL | `postgresql+psycopg2://slae:slae@postgres:5432/slae` |
| `SECRET_KEY` | Ключ підпису JWT, однаковий для всіх API-серверів | `dev-secret-change-me` (лише для розробки) |

Для реального розгортання змініть `SECRET_KEY` та пароль БД і винесіть їх у `.env`.

## 6. API (поточний стан)

| Метод | Адреса | Опис |
|---|---|---|
| GET | `/whoami` | Ім'я інстансу API (перевірка балансування) |
| POST | `/auth/register` | Реєстрація (`409`, якщо логін зайнятий) |
| POST | `/auth/login` | Вхід, повертає JWT |
| GET | `/auth/me` | Поточний користувач (потрібен токен) |

Усі запити надходять через Nginx з префіксом `/api`.

## 7. Дорожня карта

0. Каркас: Docker Compose, Nginx, два API-сервери. **Виконано**
1. БД та авторизація: моделі, Alembic, JWT. **Виконано та перевірено**
1b. HTTPS на Nginx (самопідписаний сертифікат). **Виконано, перевірено через curl**
2. Solver (метод Гаусса), Celery-задача, генерація/завантаження матриці, ліміти
3. Real-time прогрес (WebSocket + Redis Pub/Sub)
4. Історія задач, стан, скасування, ліміт задач на користувача
5. Frontend (React): вхід, форма з валідацією, прогрес, історія
6. Черга та оцінка часу очікування
7. Автоскейлінг воркерів
8. Адмін-панель

## 8. Обмеження та припущення

- Максимальний розмір матриці 5000×5000 (~200 МБ у `float64`), тому один воркер обробляє одну задачу (`--concurrency=1`).
- Конкретні значення лімітів (макс. `n`, макс. час, макс. задач на користувача) задаються в конфігурації й будуть зафіксовані у Фазі 2.
- Автоскейлінг застосовується до воркерів, а не до API-серверів: вузьке місце це CPU при розв'язанні.
- Сертифікат самопідписаний, тому браузери показують попередження. Для публічного розгортання потрібен сертифікат від довіреного центру (наприклад, Let's Encrypt).
- Значення `SECRET_KEY` і пароль БД за замовчуванням підходять лише для розробки.
