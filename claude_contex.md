# Контекст проєкту для Claude
 
Ти Senior Full-Stack Developer і System Architect. Допомагаєш мені з університетським проєктом: веб-застосунок для розв'язання великих систем лінійних алгебраїчних рівнянь (СЛАР) методом Гаусса, матриці до 5000x5000.
 
## Правила роботи
 
- Не вигадуй додаткових функцій (профілі, аватари, підтвердження пошти тощо). Лише вимоги нижче.
- Відповідай українською, пояснюй просто: я початківець у Docker і Nginx.
- Давай файли й команди покроково, завжди вказуй точний шлях кожного файлу. У командах не лишай заповнювачів на кшталт `N` чи `IP_VM` без конкретного прикладу: я вставляю команди буквально.
- Не стверджуй, що код працює, якщо його не запускали. Розділяй «перевірено в моєму середовищі» і «перевірено у користувача». Код давай малими частинами, щоб я перевіряв кожен крок.
- Я хочу іноді писати частину коду сам: для таких місць давай каркас з `# TODO` і тести, а не готовий розв'язок.
- Якщо раніше дана порада виявилась помилковою, чесно скажи про це.
- Коли даю правки в існуючий файл, вказуй, ПІСЛЯ чого саме вставити, і де саме в файлі це місце (не «в кінець», якщо там уже є інший код).
## Вимоги викладача
 
1. Розв'язання СЛАР: генерація випадкової матриці за розміром або завантаження файлу.
2. Ліміти: макс. розмір матриці, макс. час виконання. Перевищення дає негайну помилку. Валідація також на фронтенді.
3. Real-time прогрес (відсотки, поточний рядок) через WebSocket.
4. Історія задач, поточний стан, скасування, запуск нової. Ліміт задач на користувача. Дані в БД.
5. Базова авторизація (HTTPS бонус).
6. Балансування Nginx мінімум на 2 сервери (головна вимога).
7. Бонус: черга та оцінка часу очікування, якщо ресурси вичерпані.
8. Бонус: автоскейлінг контейнерів до встановленого максимуму.
9. Бонус: адмін-панель (процеси, розмір черги, навантаження серверів).
10. Обов'язково: README з архітектурою.
## Стек
 
- Frontend: чистий HTML + CSS + JavaScript без фреймворків і без збірки (рішення змінено: замість React/Vite/Tailwind, бо для двох екранів так простіше). Nginx віддає файли як статику.
- Backend: Python 3.12, FastAPI
- БД: PostgreSQL, SQLAlchemy, Alembic
- Черга: Celery + Redis
- Балансувальник: Nginx
- Контейнери: Docker + Docker Compose (Docker SDK для автоскейлінгу)
- Real-time: WebSocket (FastAPI) + Redis Pub/Sub
- Авторизація: JWT (PyJWT), bcrypt
- Розв'язувач: NumPy
## Архітектура
 
- Nginx (`least_conn`) розподіляє запити `/api/` між `api1` та `api2` (FastAPI, без стану, однаковий `SECRET_KEY`). Завершує TLS (HTTPS, самопідписаний сертифікат), всередині Docker-мережі трафік іде по HTTP. Усе інше (`location /`) Nginx віддає з `/usr/share/nginx/html`, куди змонтовано папку `./frontend` (лише читання), тож зміни у `frontend/` видно після Ctrl+F5 без перезбірки й без перезапуску Nginx. У `nginx.conf` обов'язковий `include /etc/nginx/mime.types`, інакше CSS і JS віддаються з неправильним типом.
- Postgres зберігає користувачів і задачі (статус, прогрес, помилка, часові мітки). Результат `x` не зберігається.
- Redis: брокер Celery, прапорці скасування `cancel:{id}`, та канал Pub/Sub `task:{id}` для прогресу. Воркер публікує стан задачі (`status`, `progress`, `current_row`, `n`, `error`) при старті, після кожного оновлення прогресу і при завершенні. Збій публікації не ламає розв'язування: істина про стан завжди в Postgres.
- WebSocket `/ws/tasks/{id}` (в `api1`/`api2`, `backend/app/routers/ws.py`): перше повідомлення клієнта `{"token": "..."}` (токен не в URL, щоб не потрапляв у логи Nginx). Далі сервер підписується на `task:{id}` ДО читання знімка з БД, шле знімок, потім події. Раз на 10 с тиші перечитує стан із БД і шле його (страхує від втраченої події й тримає з'єднання живим для Nginx). Після фінального статусу закриває з'єднання (код 1000); 4401 = поганий токен, 4404 = чужа або неіснуюча задача.
- Celery-воркер (`worker`, `--concurrency=1`, `worker_prefetch_multiplier=1`, результати не зберігаються) виконує `solve_task`: читає запис `Task`, генерує випадкову систему (seed = id задачі) або читає завантажений файл, викликає `solve_gauss` з гачками `on_progress` і `should_cancel`. Пропускає задачі, що вже не `QUEUED`.
- Статуси задачі: `QUEUED`, `RUNNING`, `DONE`, `FAILED`, `CANCELLED`.
- Скасування: `POST /tasks/{id}/cancel` ПЕРШИМ ставить прапорець `cancel:{id}` (TTL 1 год), потім умовним `UPDATE ... WHERE status='QUEUED'` одразу скасовує задачу, що ще в черзі (і публікує подію). Для задачі, що вже рахується, воркер перевіряє прапорець раз на 20 рядків (і на першому) та виставляє `CANCELLED`. Скасовану з черги завантажену задачу воркер пропускає і видаляє її файл.
- Історія: `GET /tasks` повертає задачі поточного користувача, найновіші першими, з `limit` (1..100, за замовчуванням 50) і `offset`. Це ж слугує «поточним станом»: активні задачі завжди серед найновіших.
- Ліміт часу: перевіряється всередині `solve_task` (дедлайн у `should_cancel`), а НЕ через Celery `soft_time_limit`: Celery бере ліміт із боку відправника задачі (API) і він перекриває налаштування воркера. Окремого жорсткого вбивства зависшої задачі немає.
- Завантажений файл API кладе у спільний том `uploads` (`/data/uploads/{task_id}.txt`, підключений до `api1`, `api2` і `worker`), воркер читає його і видаляє після завершення задачі в будь-якому статусі.
- Автоскейлер (контейнер `autoscaler`, `autoscaler/autoscaler.py`): раз на 5 с читає довжину списку `celery` в Redis. Якщо черга не порожня і воркерів менше `MAX_WORKERS` (3, разом із базовим `worker`), через Docker SDK запускає додаткові воркери за зразком базового (мітка `slae.autoscaled`, ім'я `slae-1-worker-auto-<uuid>`), пауза 15 с після запуску. Якщо черга порожня 60 с, зупиняє одного додаткового (SIGTERM: воркер дорахує поточну задачу). Базовий воркер лишається завжди. Автоскейлер монтує `/var/run/docker.sock`, що дає фактично root-доступ до VM (згадати в README).
- Міграції виконує одноразовий контейнер `migrate` (`alembic upgrade head`) перед стартом API і воркера.
### Фронтенд (`frontend/`)
- Черга й оцінка очікування: `GET /tasks/queue` (`routers/tasks.py`) для моїх задач у `QUEUED` повертає позицію серед усіх `QUEUED` (за id) і `wait_seconds = (задач попереду + задач RUNNING) / WORKER_COUNT x середній час`. Формула в чистій функції `estimate_wait` (`backend/app/queue_estimate.py`). Середній час береться з останніх 20 задач `DONE` (`finished_at - started_at`), без них діє `DEFAULT_AVG_SECONDS`. Оцінка груба: не враховує різний `n` і завищує, бо задача, що вже рахується, частково виконана. Маршрут `/tasks/queue` має стояти ПЕРЕД `/tasks/{task_id}`, інакше `queue` сприймається як `task_id` і дає `422`.
 
Один екран-сторінка, два види, що перемикаються атрибутом `hidden`: `#auth-view` (вхід/реєстрація) і `#app-view` (робота із задачами). Усі запити йдуть на відносні адреси `/api/...` і `wss://хост/api/ws/...`, тож працює і по HTTP, і по HTTPS без зміни коду.
 - Оцінка очікування: блок перед `updateTask()` (`formatWait`, `pollQueue`, `startQueuePolling`, `stopQueuePolling`). Поки є задача зі статусом `QUEUED`, раз на 5 с іде `GET /tasks/queue`, і в картці (`t.queueInfo`) показується «Позиція в черзі: N, очікування ≈ ...». Опитування стартує з `updateTask()` і зупиняється, коли в `tasks` немає `QUEUED`. У об'єкті задачі додано поля `status` і `queueInfo`.
Файли:
- `index.html`: розмітка обох видів, форми, блок `#tasks-section` зі списком `#task-list`.
- `style.css`: оформлення; правило `[hidden] { display: none !important; }` потрібне, щоб `hidden` не перебивався іншими `display`.
- `app.js`: уся логіка. Блоки в порядку розташування:
  1. Авторизація: `api()` (обгортка над `fetch`, додає `Authorization: Bearer`, повертає `{status, data}`), `errorText()` (розбір `detail` від FastAPI: рядок або список для 422), `setMode()`, `showAuth()`, `showApp()`, `login()`, `checkSession()` (перевірка токена через `/auth/me`), обробники форми й виходу.
  2. Створення задачі: `MAX_N = 5000`, `MAX_UPLOAD_BYTES = 300 МБ` (дублюють `MAX_N` і `MAX_UPLOAD_MB` з `backend/app/config.py`: змінювати ВСЕ разом), `uploadFile()` (multipart через `FormData`, `api()` не підходить), `showTaskResult()`, `parseN()` (писав я сам, регулярка `^\d+$` і діапазон 1..MAX_N, пройдено 10 консольних тестів), обробники `randomForm` і `uploadForm`.
  3. Список задач і прогрес: `tasks` (Map: id -> об'єкт з DOM-елементами, сокетом, прапорцем `finished`), `updateTask()` (малює стан; однаково годиться для відповіді REST і події WebSocket, бо поля збігаються), `ensureTask()` (створює картку, `prepend=true` для нової), `connect()` (WebSocket, токен першим повідомленням, перепідключення через 2 с при обриві, коди 4401 і 4404 обробляються окремо), `clearTasks()`, `loadTasks()` (`GET /tasks?limit=50`, для кожної незавершеної задачі відкриває сокет), `trackTask(task)` (приймає ВЕСЬ об'єкт задачі, не id), `cancelTask()`.

## Налаштування і ліміти
 
Змінні середовища (значення за замовчуванням у `backend/app/config.py`):
 
| Змінна | Значення | Призначення |
|---|---|---|
| `TASK_TIME_LIMIT` | 600 с | макс. час виконання однієї задачі (читає воркер) |
| `MAX_N` | 5000 | макс. кількість невідомих (читає API) |
| `MAX_ACTIVE_TASKS` | 5 | макс. активних (`QUEUED`+`RUNNING`) задач на користувача (читає API) |
| `MAX_UPLOAD_MB` | 300 | макс. розмір завантаженого файлу (читає API; Nginx: `client_max_body_size 300m`, міняти разом) |
| `UPLOAD_DIR` | `/data/uploads` | спільний том api1/api2/worker |
| `WORKER_COUNT` | 1 | кількість воркерів для оцінки очікування (читає API; має збігатися з реальною кількістю, у фазі 7 замінити числом від автоскейлера) |
| `DEFAULT_AVG_SECONDS` | 30 с | середній час задачі, поки немає жодної `DONE` (читає API) |

Змінні автоскейлера (сервіс `autoscaler`): `MAX_WORKERS` (3, задано в docker-compose), `SCALE_INTERVAL` (5 с), `SCALE_DOWN_AFTER` (60 с), `SCALE_UP_COOLDOWN` (15 с).
 
Інші фіксовані ліміти в коді: ім'я користувача 3-50 символів, пароль 6-72 (ті самі межі в атрибутах полів у `index.html`), токен JWT живе 24 години, `GET /tasks` не більше 100 за запит, WebSocket чекає токен 5 с. У `docker-compose.yml` блоки `environment:` поки не задають ці змінні, тож діють значення за замовчуванням; щоб змінити, додати змінну в сервіс, який її читає.
 
Секрети лежать у `.env` (не в git; шаблон `.env.example` у git): `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`, `SECRET_KEY`. Пароль Postgres (`slae`) зашитий у томі `pgdata` при першому створенні: зміна `POSTGRES_PASSWORD` без видалення тома ламає підключення.
 
Ліміт «задач на користувача» я трактую як ліміт АКТИВНИХ задач (історія не обмежується). Якщо викладач мав на увазі загальну кількість, змінити умову в `routers/tasks.py`.
 
Формат файлу матриці: `n` рядків по `n+1` числу (матриця A і стовпець b), роздільник пробіл або кома. API перевіряє форму й ліміт `n` одразу, нечислові значення ловить воркер (`FAILED`).
 
## API (поточний стан, префікс `/api` через Nginx)
 
| Метод | Адреса | Опис |
|---|---|---|
| GET | `/whoami` | ім'я інстансу (перевірка балансування) |
| POST | `/auth/register`, `/auth/login` | реєстрація (409 якщо зайнято), вхід (JWT) |
| GET | `/auth/me` | поточний користувач |
| POST | `/tasks` | `{"n": ...}`; `400` якщо n поза 1..MAX_N, `429` якщо забагато активних задач |
| POST | `/tasks/upload` | multipart-файл; `400` форма/розмір, `413` великий файл |
| GET | `/tasks` | історія своїх задач, найновіші першими; `?limit=` (1..100) і `?offset=`, інакше `422` |
| GET | `/tasks/{id}` | стан своєї задачі (чужа дає 404) |
| POST | `/tasks/{id}/cancel` | `200` якщо задача була в черзі (одразу `CANCELLED`), `202` якщо рахується (воркер зупиниться сам), `409` якщо вже завершена, `404` чужа/немає, `503` якщо Redis недоступний |
| WS | `/ws/tasks/{id}` (через Nginx: `/api/ws/tasks/{id}`) | прогрес у реальному часі, протокол див. «Архітектура» |
| GET | `/tasks/queue` | мої задачі в `QUEUED`: `[{task_id, position, wait_seconds}]`; черга спільна для всіх користувачів, порядок за id |
Усі ендпоінти, потрібні за вимогами викладача до бекенду, готові.
 
## Середовище
 
- Windows + віртуальна машина з Ubuntu, Docker працює на VM.
- Редагування через VS Code Remote-SSH (`ssh yar@localhost -p 2222`). Якщо SSH дає `Connection aborted`: VM ще не завантажилась або не працює `sshd`/мережа у VM.
- Папка проєкту на VM: `~/SLAE-1` (великі літери, Linux розрізняє регістр; Docker-проєкт називається `slae-1`). Є зайві папки `~/SLAE` і `~/slae`, їх не використовувати.
- VirtualBox, режим NAT, проброс портів: 2222 -> 22 (SSH), 8080 -> 80 (HTTP), 8443 -> 443 (HTTPS).
- Застосунок у браузері на Windows: `https://localhost:8443`. Самопідписаний сертифікат доданий у «Довірені кореневі центри сертифікації» на моєму ноутбуці (на інших машинах браузер попереджатиме).
- Swagger: `https://localhost/api/docs` з VM (або `https://localhost:8443/api/docs` із Windows).
- Гілка розробки: `develop`, репозиторій на GitHub (`yaroslavfedyshyn2/SLAE`, публічний).
- `git push` по HTTPS не приймає пароль акаунта GitHub: у полі `Password` потрібен Personal Access Token (classic, право `repo`) або SSH-ключ. Читання публічного репо токена не потребує, запис потребує.
## Поточний стан
 
Виконано (підтверджено мною):
- Фаза 0: Nginx балансує між `api1` і `api2`.
- Фаза 1: таблиці `users`/`tasks`, Alembic, register/login/me з JWT, перевірено в БД і запитами.
- HTTPS на Nginx (самопідписаний сертифікат): перевірено через `curl -k` з VM і в браузері через проброс 8443. Редирект HTTP -> HTTPS свідомо не зроблений (порт 80 залишено для внутрішніх перевірок).
- Секрети винесено в `.env`.
- Фаза 2: solver Гаусса (`backend/app/solver.py`) із вибором головного елемента, прогресом і скасуванням; Celery-воркер і `solve_task`; ендпоінти `POST /tasks`, `POST /tasks/upload`, `GET /tasks/{id}`; ліміти. Скасування перевірено на моїй VM (`CANCELLED`).
- Фаза 3: воркер публікує стан у `task:{id}`, WebSocket `/ws/tasks/{id}` пересилає його клієнту. Перевірено в середовищі Claude (тести зі справжнім Redis) і на моїй VM (потік `RUNNING` до `DONE` через Nginx, Python-скрипт у контейнері `api1`).
- Фаза 4: `POST /tasks/{id}/cancel` і `GET /tasks`. Перевірено в середовищі Claude і на VM (запущена задача зупинилась на 2% зі статусом `CANCELLED`; список у порядку від новішої до старішої).
- Завантаження файлу: том `uploads` підключено до `api1`, `api2`, `worker`; `backend/sample_100.csv` на VM дає задачу `source: upload`, `n: 100`, `DONE`.
- Фаза 5 (фронтенд на чистому HTML/CSS/JS), підтверджено мною в браузері:
  - Nginx віддає `frontend/` (крок 1).
  - Вхід і реєстрація, сесія після входу (екран «Користувач: test1»).
  - Створення випадкової задачі: `n = 3000` дає «Задачу створено», `n = 5001` дає повідомлення з фронтенду без запиту до API, тест `parseN` (10 перевірок) пройдено.

## Практичні уроки (щоб не повторювати)
 
- Код бекенду копіюється в образ при збірці: після зміни коду `api` або `worker` потрібно `docker compose up -d --build`, інакше контейнер працює зі старим файлом (воркер не бачив `solve_task`, поки не перезібрали; новий ендпоінт давав `404 Not Found`, поки не перезібрали API). Фронтенд НЕ потребує збірки: папка змонтована, достатньо Ctrl+F5.
- Довгі вставки у VS Code Remote-SSH іноді обрізаються (так було з `docker-compose.yml` і з командою `curl`). Після вставки перевіряти `tail` файлу і `docker compose config > /dev/null && echo OK`.
- У `docker-compose.yml` відступ вирішує, чиє поле: `volumes:` має стояти на 4 пробілах поруч із `build:` і `depends_on:`. Зі зсувом під `depends_on` буде помилка `depends_on.volumes must be a mapping`. Спершу `docker compose config`, і лише потім `up`.
- Команди з кількох рядків, вставлені разом, виконуються всі підряд, навіть якщо перша впала. Для кроків із перевіркою вставляти по одній команді.
- Ніколи не `docker compose down -v`: це видаляє том із базою.
- Після перестворення API-контейнерів Nginx може дати `502`: `docker compose restart nginx`. Якщо `curl` до `localhost:443` дає `Failed to connect`, Nginx зупинений: `docker compose up -d` його піднімає.
- Для діагностики просити вивід текстом, а не скріншотом (пробіли й відступи важливі). Для помилок у браузері: F12, вкладка Console, лише червоні рядки з `app.js`. Жовті попередження з `contentscript.js` (`MaxListenersExceededWarning`, `ObjectMultiplex`) приходять від розширень браузера й до проєкту не стосуються.
- `python` у `docker compose exec -T` буферизує вивід у pipe: для живого потоку використовувати `python -u` і `print(..., flush=True)`.
- Воркер бере задачі по одній: n=5000 займає ~2 хв, тож для тестів ставити n=3000 (~30 с) і не накопичувати чергу.
- Годинник VM може відставати після призупинення VM (було ~1,5 год): часові мітки в БД тоді не збігаються з реальним часом. Виправлення: `sudo timedatectl set-ntp true`.
- Фронтенд: при правках у `app.js` частини з минулих кроків легко залишити старими. Типова помилка: `trackTask(resp.data.id)` замість `trackTask(resp.data)` дає «Задача №undefined» і `non-finite` у смузі прогресу. Другий рядок-пастка: `setMode("login"); checkSession();` мають бути останніми у файлі.
- Браузер кешує `app.js`: після правок завжди Ctrl+F5.
- `docker compose up -d --build` під час розрахунку перезапускає воркер: задача лишається в БД зі статусом `RUNNING` назавжди, а повідомлення в Celery може загубитись (задача застрягає в `QUEUED`). Це завищує оцінку в `/tasks/queue` (`running` рахує завислу задачу). Лікування вручну: `update tasks set status='FAILED', error='Worker restarted', finished_at=now() where id=...`, а застряглу в черзі поставити заново: `solve_task.delay(id)`. Автоматичного відновлення немає (записати в README як відоме обмеження). Перед перезбіркою дочекатись, поки черга порожня.
- Імена контейнерів, створених у циклі, не робити з `int(time.time())`: два в одну секунду дають `409 Conflict`. Використовувати `uuid.uuid4().hex[:8]`.
